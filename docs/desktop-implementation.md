# SchoolWork implementation plan

Inspected commit: `1e1e456ee0e7bd96a499912787c2dd837e088569` on `SILLEN69/schoolwork-desktop/main`.

## Architecture and decisions

The app is React/Vite inside an isolated Electron renderer. `electron/main.ts` owns TeachGPT requests, Zod tool validation, sequential task execution, cancellation and IPC. `preload.ts` exposes a narrow bridge. `provider.ts` already serializes arbitrary message content for OpenAI-compatible streaming Chat Completions; `agentRequest.ts` recovers incomplete inference without executing partial actions. SQLite stores text messages, task metadata and tool records. Process tools use Windows user permissions, not a sandbox. The current Markdown renderer lacks math and syntax highlighting, the composer sends text only, and no desktop automation exists.

1. **Message UI:** add remark-math, KaTeX and syntax highlighting; normalize common LaTeX delimiters while preserving code; improve code headers/copy feedback, tables, lists and equation overflow. Render existing saved messages using the same component.
2. **Attachments:** local PNG/JPEG only, decoded and re-encoded in main with size/pixel/count limits. Keep UUID-addressed files under app user data and a SQLite metadata table with conversation/message ownership. Expose select/import/read/remove IPC with trusted main-frame checks. Show thumbnails, clipboard/drop support and image-only sending. Never send local paths to the provider as image URLs. WebP is deliberately excluded because Electron's cross-platform native image decoder officially supports PNG/JPEG.
3. **Provider input:** hydrate persisted attachment references into user content arrays with text and `image_url` data URIs only immediately before inference. Keep images out of redaction, character-based text compaction, diagnostic records and persisted pending requests. Bound the number of recent images. Surface image rejection clearly; do not silently drop images or switch models. Test vision using a synthetic image with the configured account only; do not upload the user's screen as a capability probe.
4. **Model capability:** store a separately checked vision profile per model (unknown/verified/unsupported). `/models` IDs alone do not prove vision. A UI test sends a synthetic picture and checks its answer. Screenshot tools attach actual pixels to the next inference; screenshots remain useful locally even with text-only models, while UI Automation supplies bounded text observations. Full visual interpretation requires a vision-capable TeachGPT model.
5. **Windows backend:** bundle a small .NET Framework C# helper built with Windows' existing compiler. No separate runtime installation and no generated PowerShell scripts. JSON lines over private process pipes; no HTTP listener. Win32 enumerates and focuses windows, SendInput controls mouse/keyboard, UI Automation reads controls, and GDI captures a visible selected window/screen in physical pixels. This avoids Electron native Node ABI dependencies. Capture requires a visible, foreground window for window-scoped operations; obscured/minimized windows must be focused first. Protected content may appear black.
6. **Tools:** `list_apps`, `launch_app {appId}`, `list_windows`, `focus_window {windowId}`, `inspect_window {windowId}`, `capture_screen {windowId?}`, `click {screenshotId,x,y,button}`, `type_text {screenshotId,text}`, `key_press {screenshotId,keys}`, `scroll {screenshotId,x,y,amount}`. Register schemas and executors in both native and JSON fallback protocols. Prefer UI Automation plus screenshots to guessing. Each input consumes a recent observation, verifies target identity/bounds/focus and reobserves after acting.
7. **Capabilities:** settings for app launching, screen viewing and control, with an executable allowlist managed by the user; snapshot at task creation and intersect with current settings for immediate revocation. No per-action confirmation dialogs. Existing arbitrary PowerShell/process execution can bypass these app-level controls; document that limitation rather than claim isolation. Restrict tool registry by effective capabilities, and enforce again at dispatch.
8. **Lifecycle:** cancel/pause terminates pending helper work and invalidates observations; app exit cleans up its helper only. User apps stay open. Helper errors/timeouts are surfaced as uncertain outcomes rather than automatically repeating input. Require an unlocked Default input desktop, reject lost/reused windows and report UIPI/elevated/UAC restrictions. Do not elevate the app. Screenshots are transient; user uploads persist with their conversation; unattached uploads expire and chat deletion removes owned files. No continuous recording, microphone capture, or automatic screen-memory ingestion.
9. **UI:** composer attachment tray and screen capture button; clear capability status and stop control; Desktop panel with selected applications, current windows and screenshot inspection. Preserve task timers, file access and activity. Support English/Swedish labels. Desktop controls never live in the embedded website preview.

## Phases and acceptance checks

1. Rendering: the supplied Swedish physics example renders fractions/root signs; fenced JS/Python has token colors, copy preserves text, wide equations/code/tables scroll inside messages. Test malformed math and untrusted HTML.
2. Attachments/provider: imports and reloads survive restart; file/count/pixel/ownership limits work; image-only chat sends; text compaction leaves image references valid; rejected vision requests produce a useful error.
3. Windows helper: build and pipe-protocol test on Windows; enumerate/capture/inspect a disposable test window; click/type Unicode/key/scroll have observable effects; stale screenshots and wrong focus are rejected; cancellation kills only owned helper work.
4. Integration: register tools, hydrate screenshots for inference, show Desktop panel and capability settings. Test native and JSON action paths, capability revocation, helper restart and old-conversation compatibility.
5. Delivery: full test suite, TypeScript/Vite/Electron build, rendered screenshots at wide/narrow window sizes, Windows package build with helper included. Push the verified change to GitHub and provide a local package. State separately which local checks passed and whether live TeachGPT vision was actually verified.

### Limits of verification

Automated local tests can verify image transport and UI but cannot establish a school-hosted model's visual reasoning quality. Elevated/UAC behavior follows Windows integrity restrictions. Screenshot capture is a point-in-time visible desktop observation, not a video stream or guaranteed capture of protected/occluded content.

All eight requested files were read before selecting the desktop architecture. The inspected baseline is pinned above, not inferred from the screenshot:

| `electron/processTools.ts` | Direct processes and PowerShell already run as the current Windows account; process ownership/cancellation exists. | Keep these tools unchanged. ### IPC contract

Renderer-facing methods are `chooseImages(conversationId)`, `importImage({conversationId,name,base64})`, `readImage({conversationId,id})`, `removeImage({conversationId,id})`, `desktopApps()`, `chooseApplication()`, `desktopWindows()`, `captureScreen({conversationId,windowId?})`, `setCapabilities(capabilities)`, `stopDesktop()` and `testVision(model)`. `send` additionally accepts `attachmentIds`. `getChat` returns message attachments and unsent draft references. A transient screenshot event carries the pixels to the Desktop panel; a settings-change event updates the Stop status even when no task is active. Every handler validates the main renderer and main frame; schemas validate counts, IDs and arguments again.

`importImage` accepts bytes, not arbitrary filesystem paths. File-dialog imports check file size before reading. Imports are serialized to prevent parallel requests bypassing the six-image limit. Send rejects duplicate, foreign-conversation or already-sent IDs. Conversation deletion removes owned image files. Draft cleanup and orphan cleanup stay inside the attachment directory and remove only generated UUID image names.

### Desktop schema and coordinate contract

`windowId` is an opaque decimal HWND string; application IDs are canonical executable paths from the Settings list. Input arguments never accept an arbitrary PID/path supplied by the model. `click` supports left/right buttons, `type_text` supports up to 4,000 Unicode characters, `key_press` supports named shortcuts, and `scroll` limits wheel delta to ±2,400. These are basic desktop controls; drag gestures/double-click timing are not promised in this phase.

A window observation records HWND, PID, executable, physical bounds, focused state, resized image size, owner task and creation time. Each screenshot token is one-use and expires in 30 seconds. Image-relative coordinates are mapped back to physical desktop coordinates, including negative monitor origins. The helper rechecks identity, unchanged bounds and focus; clicks additionally reject a point covered by another window. Resized/partly off-screen windows are rejected rather than silently clipped. UI Automation is bounded and omits password controls. Selecting a launcher whose real process uses another executable requires selecting that running executable too.

Full-screen capture intentionally means the primary display and may include non-selected applications; the allowlist restricts window operations/input, not visible pixels in a requested full-screen shot. No background polling or screen recording is introduced. Native screenshots use GDI and do not guarantee capture of DRM/protected content. Win32 input remains subject to [Windows integrity restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput); no UAC/elevation workaround is included.

### Image/provider and model contract

Immediately before inference, recent saved images become user content parts of the form `[{type:"text",text:"…"},{type:"image_url",image_url:{url:"data:image/png;base64,…",detail:"auto"}}]`. Screenshots use JPEG data URIs. Internal observation markers are stripped from wire messages. The latest two image-bearing saved messages and at most one transient screenshot are retained; older omitted images are explicitly identified. Image bytes do not consume the text-only compaction budget, but count/byte bounds still apply. Saved pending requests and tool results exclude image bytes, and diagnostics record only sizes/timings/status.

Vision profiles are separate from streaming/tool support and reset when credentials change. Unknown models can be tried; image rejections become recoverable errors, without silently dropping a user's image or changing their model. For a known unsupported model, a screen capture is identified as local-only and the model is directed to text UI Automation. The sample-image test belongs in the real app profile because an isolated test cannot necessarily decrypt an installed profile's protected credential. Support is unknown until that live test succeeds; accepting the array alone does not prove visual reasoning.

### Dependencies and trade-offs

Production additions are `remark-math`, `rehype-katex`, `katex`, `rehype-highlight` and `mdast-util-from-markdown`. KaTeX fonts are bundled locally. Playwright is a development-only dependency for Electron verification. The native helper references the Windows .NET Framework drawing/forms/serialization/UI Automation libraries and is compiled by `scripts/build-native.mjs`, then copied with `extraResources`. This avoids a Node/Electron ABI-sensitive native automation addon and does not require installing a service or administrator rights. Windows x64 packaging is the supported target. PNG/JPEG are the deliberately supported uploads, matching [Electron's documented image formats](https://www.electronjs.org/docs/latest/api/native-image).

## Verification record

- Unit suite: 70 tests pass, including math/code rendering, unsafe HTML/links, image ownership/count/pixel limits, transaction rollback, draft expiry/orphan cleanup, provider recovery, screenshot coordinates/ownership/expiry and helper cancellation/timeout/restart.
- Real Electron integration: isolated SQLite/settings and a disposable WinForms window; both native tools and constrained JSON fallback complete screenshot → click/type → recapture → keyboard/scroll → inspect loops. Actual Unicode/multiline text, a button click and scroll are observed. UI Automation omits the password field. Screenshot pixels reach the mock provider and are absent from persisted tool results.
- Rendered UI: wide and 940-pixel application layouts, fractions/roots/units, syntax colors, exact Copy contents, saved image previews and no horizontal document overflow. Screenshots are retained with this deliverable.
- Packaged application: Windows installer and portable build succeed. The packaged 0.4.0 executable starts with an isolated profile, restores saved SQLite messages/image previews, loads bundled KaTeX assets and captures the disposable window with its bundled native helper. The existing installed app was not closed or overwritten. Generated packaging files were moved to E: after C: ran low on space.
- Launch/rejection integration: the selected disposable executable is actually launched; an HTTP 400 image rejection produces the unsupported profile and a recoverable task while preserving its attachment. Provider traffic in these checks is mocked, not claimed as live TeachGPT verification.
- Windows focus protection: Windows refusal was observed during testing. The fixture explicitly simulates activation of its own editor before the successful control test. SchoolWork itself still reports refusal instead of stealing focus or bypassing Windows rules.
- Production dependencies: audit reports no known production vulnerabilities. Two existing moderate development-only Vitest advisories remain; no forced major test-runner migration is included.
- Live TeachGPT vision: **not verified**. The isolated probe could not decrypt the installed application's protected credential; no user screen was uploaded as a probe. Run the synthetic-image check in the installed app's Settings.
- Remaining manual coverage: actual school-hosted visual reasoning quality, 125/150% and mixed-monitor DPI, elevated/UAC/locked desktop cases, protected video, and each third-party application/packaged-app launcher. Those are not claimed to be proven by the disposable-window test.
